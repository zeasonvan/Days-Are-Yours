# Refactor decision

## 评分

| 维度 | 旧插件 | 说明 |
| --- | --- | --- |
| 代码质量 | 3/5 | 单文件 1193 行，分区靠注释 |
| 架构合理性 | 2/5 | 无分层、无核心引擎导出 |
| 功能完整性 | 2/5 | 只有退休 + 假期 + 自定义假期 |
| UI | 3/5 | 后期已改为一列 + 双卡，但仍单页 |
| 可维护性 | 2/5 | 无测试、无 Git、无文档 |
| 扩展能力 | 1/5 | 新增模块会继续堆大文件 |
| 数据安全 | 4/5 | 本地优先、无上传 |
| Harness 兼容 | 5/5 | 已验证可安装、可渲染 |

## 三个方案

- **A 逐步升级**：在 1193 行单文件上继续加 7 个模块 → 预计 4000+ 行，不可维护。
- **B 保留架构重构**：仍是一个文件，但整理分区、补测试 → 能撑到 v1.1，撑不到 v2。
- **C 新建工程 + 迁移已验证代码**：新包 `@local/days`，旧包保持安装，核心算法与数据迁移过来 → 可长期维护，可回退。

## 选择：C

理由：

1. 旧插件的业务算法（退休规则、假期区间、日期工具）经过真实使用与修复，价值高，直接复制并补测试。
2. 单文件结构不适合七大模块，新工程按「copy / dates / policy / holiday / store / engines / views / styles / registration」分区。
3. 旧包完整保留在 `countdown/` 且已备份，DAYS 安装验证通过后才停用旧 bundle，用户可随时回退。
4. 数据迁移只读旧 key，不修改旧数据。

## 验收门槛

- `node tests/check.mjs` 全绿（日期、退休、假期、请假、拼假、工作状态、迁移）。
- `plugin_manager install_bundle` 返回 `application: applied`。
- 旧插件仍可重新启用。
